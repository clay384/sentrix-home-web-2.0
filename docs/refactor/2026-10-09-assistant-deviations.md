# 助手链路：与 1.0 的偏离登记（2026-10-09）

依据 `docs/refactor/2026-10-08-assistant-fixes-implementation-plan.md` 的 §3.1–§3.8。
**这份文档只登记「2.0 故意不照 1.0 做」的地方**；逐项的实施内容与判据在看板文档 §3。

---

## D1 · 工具计价口径：被拒也计价（§3.4A）

| | 1.0 | 2.0 |
|---|---|---|
| 计什么 | 只有 `status == "ok"` 的调用 | **所有工具往返**（成功 / 被拒 / 失败 / 回放） |
| 位置 | `agent_runtime/tool_policy.py:61-62` | `TaskState.tool_round_trips` |

**理由**：1.0 那条口径的前提是**被拒就 `break` 结束回合**（`runtime.py:3318`）——拒绝根本
不会再来一次，所以不必再罚一次预算。2.0 把拒绝当普通工具结果发回、允许模型重试，同一件
事**照常烧掉一个模型步**：实测 762 次被拒里 **426 步是「整步全被拒」**，占全部 2667 步的
16%，而被拒之后模型有 **51%** 继续试同一个工具。

修完之后，「工具往返数」被硬限死在 6，而每次往返恰好 1 个模型步 →
`6(往返) + 1(作答) + 1(L2 评审) = 8 = max_steps`，**那条不变量才真的成立**。在此之前它
只是假成立：被拒可以额外吃步，模型于是能一路试到步数耗尽——`step_budget_exhausted` 的
123 道里 118 道**恰好用满 8 步**，102 道判 0、2 分一道没有。

**代价**：一轮能做的取证少了一次（被拒的尝试现在占额度）。这是有意的——被拒的尝试本来
就不产出任何东西，而它此前唯一的效果是把模型步吃光。

## D2 · JIT 剪枝的效力：剪掉即不能调（§3.2）

| | 1.0 | 2.0 |
|---|---|---|
| 剪枝作用面 | **只作用于提示词渲染**（`runtime.py:1877`） | **也作用于能力**（原生 `tools` 字段） |
| 准入白名单 | `profile.tools`（`runtime.py:1764`） | 就是 `select_tools` 的返回值 |

**理由（这条是结构性的，不是偏好）**：1.0 的工具调用是「模型在正文里写 JSON」，运行时
拿 `profile.tools` 做准入——所以剪掉一个工具，模型**看不见它，但仍然能调它**。2.0 走原生
`tools` 字段，那份数组**既是广告也是约束**：剪掉 = 物理上不能调。

**后果与应对**：2.0 的选择规则一律**比 1.0 的渲染清单保守**——只剪「现在根本用不上」的，
不剪「这一轮后面可能还要用」的。具体一处最要紧的差别：`get_result_page` **只要已经有
结果集就一直在**，不按 `photo_set` 是否销账来剪。1.0 在 `photo_set` 被满足后会把翻页从
渲染清单里去掉（模型仍能调），2.0 照做就等于把「看第 7–12 张候选」这个能力整个拿掉。

## D3 · 规划提示词的 `delivered_photo`（§3.6，**已于 2026-10-10 回退**）

> **回退记录。** 下面那个「只有用户明确要看图时才声明」的收紧**方向是错的**，已回退成
> **「非普通聊天就声明」**。理由：判据不是「用户有没有说要图」，而是「**这是不是一道关于
> 相册的真问题**」。用户指着一张婚礼合影问「这是在哪儿拍的」——他没说「给我看看」，
> 但他要的显然就是那张照片的答案。收紧后实测声明数从 212 道掉到 **51 道**，而
> 「检索找到了 GT 却没交图」的 181 道里 **168 道是根本没声明 `delivered_photo` 的**。
>
> 现在用的判据 1.0 也没有（1.0 只要声明 `photo_set` 就无条件同时声明，212:3 说明太宽）：
> **非普通聊天就声明**，普通聊天交给模型自己判——它读得到整句话，比在这里跑关键词正则准。
>
> 下面保留原文，作为「这个方向试过了、不行」的记录。

### 原始记录（已回退）

| | 1.0 | 2.0 |
|---|---|---|
| 原文 | 「用户想看照片、要求展示、或问「有没有……的照片」时，声明 `photo_set`；**同时声明** `delivered_photo` 表示「要把照片真的交到用户手上」……」 | 「……**只有**用户明确要看图（「给我看看 / 我想看 / 有没有……的照片 / 发几张」）时，才**同时**声明 `delivered_photo`。只是「问关于照片的事」**不要**声明」 |

**理由**：1.0 那句后半段无条件，于是 `delivered_photo + photo_set` 成了默认模板。实测
487 道题里 **212 道**声明了 `delivered_photo`，而问题文本里真正要求看图的只有 **3 道**。
`delivered_photo` 声明了却没交付会走 `answered_with_gap`，而 §3.5 的提醒也是按它触发的
——多声明的直接代价是每一道这样的题都多一次模型步的提醒。

**这条门禁是弱的**（`test_delivered_photo_is_declared_only_when_the_user_asked_to_see_photos`
只是文本断言）。真正的验证是重跑后「声明了 `delivered_photo` 的题数」从 212 降下来。

## D4 · 删掉 `delivery_contradiction`（§3.7）

1.0 有这条规则（`final_guard.py:106-112`），2.0 **删除**，连同它唯一的输入
`GuardFacts.delivery_state` / `delivered_count`。理由与判据见
`domain/assistant/final_guard.py` 的 `_delivery_completeness` docstring（两段：
输入取不到、前提已变）。

一句话版本：规则设计于「省略的时代」（1.0 的 final 有 49% 根本不带
`selected_image_handles`）；2.0 把那个字段做成必填之后，零交付是**明确写下的 `[]`**，
不是遗漏——拦它等于打回模型的显式选择，还会在约 300 道「检索取完但没交图」的题上各花
一个模型步。

## D5 · 暴露候选集是一次有意的契约放宽（§3.8）

2.0 的助手 HTTP 契约此前**不暴露检索候选集**，`behaviour-baseline.md` 的
「2.0 不再暴露的轨迹」一节把它记成一条**已知缺口**。本次把它补上：
`agent_turns` 加一列（迁移 0012）、终态载荷加 `retrieved_candidates`。

**理由**：不补这一格，评测侧只能拿**交付集**冒充检索集——`retrieval_media_refs` 被直接
赋成 GT，分母是 GT、分子是交付集，394 道零交付的题 recall 一道不差全是 0.0。**「检索没
找到」与「找到了没交付」在指标上完全一样**，而归因表因此只是「没交付」的影子
（`primary.R` 在 424 道题上亮红）。

契约放宽的代价是 openapi 契约要重导（已做），以及 `behaviour-baseline.md` 那一行要改
（已做）。**这不是「顺手多给一个字段」**：它是让下游能分锅的前提。

## 记一笔：不做的

| 项 | 理由 |
|---|---|
| 1.0 的 `recommended_handle`（关键词匹配版） | 同一个问题用 §3.1 的 `level` + 检索排名解决——那是数据，不是字面匹配 |
| 1.0 的 `recommended_resolution` | 与规划器重复、硬编码题型词（`合影\|聚餐\|旅行`）、判据在问题文本上、未验证 |
| 1.0 的第四条提醒（`is_candidate_mode` 的「你尚未检索相册，禁止直接猜测回答」） | 它**没有** `prompted` 标志（不是一次性的），会一直拦；2.0 已有 `MIN_REQUIREMENTS = 1` 堵住零需求 |
| `HISTORY_LIMIT = 8` | 不是回归。真正的缺口是**多轮会极快耗尽上下文窗口**，而 1.0 也没真正设计过多轮对话。登记为已知缺口 |

## D6 · `group_photo_*` 的判据换成数据（§7.4）

| | 1.0 | 2.0 |
|---|---|---|
| 何时计算 | **只有问题里出现「合影」两个字时**（`tools.py:1085` 的 `re.search(r"合影", …)`） | **总是** |
| 人数从哪来 | 正则从 `caption` / `activity` 的中文散文里抠「N名 / N人」（带一张中文数字表） | 人脸绑定 + 观察快照（与 `query_photo_people` 同一套算法） |
| 字段 | `group_photo_count` / `group_photo_sizes` / `group_photo_rows`（含 `description: caption[:240]`） | 同名字段与形状；**去掉 `description`**（preview 里已有 `evidence_summary`）；另加每条 preview 的 `people_count` |

**理由**：见计划文档 §7.4。要点是 1.0 的判据与 §4 已经否掉的 `recommended_resolution`
同类（硬编码题型词），而它服务的只有 487 道题里的 1 道；`people_count` 还顺带补掉另一个
洞——`people` 只有已确认的人名，只看它会把「四个人合影、认出来一个」读成「一个人」。

### 2026-10-26：显式 native 实验预算与操作证据

在 native 模式允许四项工具次数预算以准确环境字符串 `null` 关闭，仍执行显式模型步和墙钟；不更改 legacy 默认。Planner单独记录，native主循环/L2/上下文恢复/forced final共用30步，强制收尾不再获得预算外第31次调用。工具帽/收尾时间预留实际限制执行时记录budget_events，末尾已超墙钟也记录；PhotoBench排除这些题的质量评分并保留真实答案及轨迹。模型发现失败不再仅有泛型ModelServiceError，供应商内容过滤/无效响应也保留操作类型。此偏离遵循用户“所有限额或供应商故障必须明确，不得当架构回答质量0”要求；并不修改正常错误答案、合法模型拒答和不合法tool arguments的评分规则。
