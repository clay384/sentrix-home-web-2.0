## 2. 启停

### 2.1 make 目标（推荐）

**【转录】**（`Makefile` 的 `install-services` / `start` / `stop` / `restart` / `status` 目标）：

```bash
cd ~/Github/sentrix-home-web2.0

make install-services   # 把仓库里的单元拷到 ~/.config/systemd/user/ 并 daemon-reload
make start              # 起两个 --user 服务（9598 + 9597）
make stop               # 停两个
make restart            # 重启两个
make status             # 看两个的状态
```

**【实测】** `make status` 输出正常；两个单元均为 `active (running)`、`enabled`。

### 2.2 直接走 systemctl（单服务操作）

**【实测】**：

```bash
systemctl --user start|stop|restart sentrix-api.service        # 只管 9598
systemctl --user start|stop|restart sentrix-photobench.service # 只管 9597
systemctl --user is-active  sentrix-api.service sentrix-photobench.service
systemctl --user is-enabled sentrix-api.service sentrix-photobench.service

journalctl --user -u sentrix-api -f          # 跟日志
journalctl --user -u sentrix-photobench -f
```

**两个单元互不依赖**：【转录】+【实测】停 9598 不影响 9597，反之亦然；
两个都停也不影响 8500 / 8100 / 8101 / 8102（2.0 不碰它们）。

### 2.3 ⚠️ 单元是「**拷贝**」不是符号链接

**【实测】**（`ls -la ~/.config/systemd/user/sentrix-api.service` 是 `-rw-r--r--` 普通文件）：

单元源文件在仓库的 `deploy/systemd/`：

```
deploy/systemd/sentrix-api.service
deploy/systemd/sentrix-photobench.service
```

`make install-services` 做的是 `install -m 0644 <仓库> ~/.config/systemd/user/` + `daemon-reload`
——**拷贝，不是 symlink**。所以：

> **改了仓库里的单元文件之后，必须重跑 `make install-services`，否则跑的还是旧拷贝。**
> 只 `daemon-reload` 没用——systemd 读的是 `~/.config/systemd/user/` 里那份。

**【实测】** 反证：本机两份都是普通文件（非链接），修改仓库单元后不会自动生效。

## 3. 两个容易踩的坑

### 3.1 `systemctl --user` 需要 `Linger=yes`

**【转录】**（机制）+【实测】（本机取值）：`systemd --user` 的服务默认**在用户登出时被停掉**。
要让它登出后继续跑，必须给该用户开 linger：

```bash
loginctl show-user asus -p Linger      # 期望 Linger=yes
# Linger=yes                          # ← 本机实测就是这个
loginctl enable-linger asus            # 没开时打开（需要 sudo / polkit）〔未实测〕
```

**【实测】** 本机 `Linger=yes`，所以两个单元登出后仍在跑。
**没开 linger 的症状**：SSH 一断、服务就没了，而 `systemctl --user status` 在断线前看起来一切正常。

### 3.2 端点注入走 **drop-in** —— 查「2.0 在跑哪个模型」看这里

**【转录】**（`apps/photobench/src/photobench/infrastructure/deploy/systemd_process.py`）：

2.0 的模型端点是**启动时读死**的环境变量 `SENTRIX_VLM_BASE_URL`（`sentrix.config.Settings`
的 `env_prefix="SENTRIX_"` + 字段 `vlm_base_url`）。所以 PhotoBench 的「**换模型 = 重启 2.0**」
这条链，是靠**写一个 drop-in 覆盖文件再重启**实现的：

```
~/.config/systemd/user/sentrix-api.service.d/10-sentrix-vlm-endpoint.conf
```

内容形如：

```ini
[Service]
Environment="SENTRIX_VLM_BASE_URL=<端点 URL>"
```

写文件 → `systemctl --user daemon-reload` → `systemctl --user restart sentrix-api.service`。

> **手工排查「2.0 到底在跑哪个模型」时，看 drop-in，不要只看 `deploy/systemd/` 里的单元文件。**
> 单元文件里根本没有这个变量（它靠默认值 + drop-in 覆盖）。

**查当前生效值（权威来源）**：

```bash
systemctl --user show sentrix-api --property=ActiveState --property=Environment
# ActiveState=active
# Environment=SENTRIX_VLM_BASE_URL=http://127.0.0.1:18100/v1
systemctl --user cat sentrix-api        # 看单元 + 所有 drop-in 合并后的结果
```

**【实测 · 2026-10-06】** 本机**有** `sentrix-api.service.d/10-sentrix-vlm-endpoint.conf`，
指向 ninfer。在此之前跑的是 `sentrix.config` 的**默认端点** `http://127.0.0.1:8100/v1`
——**而 8100 已经不在运行**，所以那时 2.0 调不到任何模型（症状是静默的：`/api/v1/health`
仍回 `ok`，因为它只看库）。改指与验证见 §3.3。
**drop-in 只在「换过模型」之后才会出现**；它的**存在与否本身就是运行状态的一部分**。

> 这条链**只有在设了 `PHOTOBENCH_SENTRIX_SERVICE_UNIT` 之后才走 systemd**（见 §4.1）；
> 没设时走裸进程路径，写的是 `apps/photobench/logs/sentrix-process.json`，不是 drop-in。

### 3.3 2026-10-06：端点从 8100 切到 ninfer（18100）

**为什么切**：8100 的 llama-server **不在运行**，而 1.0 的 8771、2.0 的 9597、2.0 的 9598
四处配置都还指着它。同时本机跑着一个 **ninfer** 推理引擎（`~/Downloads/GoQuark/`，
**独立于两个仓库的第三方项目**，C++ 写的，用自有 `.ninfer` 模型格式），端口 18100。
1.0 的 PhotoBench 已经在用它——`results/` 里 2026-10-05~06 的 11 个 run 全是
`qwen3.8-27b-graft-8k-k8v4-c4-cpuvision`。**2.0 用同一个模型才谈得上与 1.0 对照。**

**怎么切的**（两处，必须一致）：

| 位置 | 内容 |
|---|---|
| drop-in `10-sentrix-vlm-endpoint.conf` | `Environment="SENTRIX_VLM_BASE_URL=http://127.0.0.1:18100/v1"` |
| `apps/photobench/config/runtime_connection.json` | `model_base_url` 同上、`endpoint_model` 改成实际探测到的 model-id |

**【实测】端到端验过**（不是只看 health——`/api/v1/health` 只报库，`database: ok`
对一个不可达的模型端点一个字都不会说）：

```
POST /api/v1/assistant/conversations        -> conv_...
POST .../turns  {"message":"请只回复两个字：收到"}
GET  /api/v1/assistant/turns/...           -> result.answer = "收到"
```

外加一条独立证据：**ninfer 自己的计数器涨了**
（`committed_decode_tokens` 1054333 → 1055536、`computed_prefill_tokens` 8953427 → 8957563，
取自 `http://127.0.0.1:18101/stats`）——证明请求真的穿过了模型，而不是 2.0 自己编了句话。

> **换端点不需要改代码**：2.0 主 API 刻意不配模型名，启动后问端点的 `GET /v1/models`
> 自己拿（`sentrix/config.py` 记着 2026-09-24 的教训：8100 从 llama.cpp 换 vLLM，写死的
> `gemma4-qat-iq3xxs` 立刻 404）。所以只要 drop-in 指对，模型名是自动的。
>
> **回退**：删掉 drop-in + `daemon-reload` + `restart`，即回到默认的 8100。

## 4. 两条必须设的配置（不设则行为与预期不符）

### 4.1 `PHOTOBENCH_SENTRIX_SERVICE_UNIT=sentrix-api.service`

**【转录】**（`photobench/config.py:96`、`bootstrap/container.py:190-197`）：

PhotoBench 在「换模型 = 重启 2.0」时，**有两个实现**，按这个环境变量选：

| 值 | 用的实现 | 行为 |
|---|---|---|
| **空（默认）** | `SubprocessSentrixProcess` | **裸进程**：按端口 `lsof -sTCP:LISTEN` 反查、SIGTERM、再 `Popen` 起一个 `make dev` |
| 非空（如 `sentrix-api.service`） | `SystemdSentrixProcess` | 走 `systemctl --user restart`，端点读单元的有效环境 |

**生产要真正接管到 systemd，必须设它**（值 = `sentrix-api.service`）。
默认（空）意味着 PhotoBench 会**用裸进程方式去掐 systemd 管的 9598**——那不是期望的行为。

**【2026-10-07：已补上，且实测后果比本文原先写的严重】**

原先这里记的是「**没有设**……生产走裸进程路径，**那不是期望的行为**」。
真正跑一轮评测才知道：**不是「不期望」，是直接坏掉。**

实测链条（跑 PhotoBench 时）：

1. 走裸进程路径 → `lsof -sTCP:LISTEN` 反查 9598 的 pid → SIGTERM → 再 `Popen` 一个 `make dev`；
2. 那个新进程**绑不上端口**：`ERROR: [Errno 98] error while trying to bind ('0.0.0.0', 9598): address already in use`；
3. 9598 整个不可用，评测的 `photo_import` 阶段 500。

更早一次（2026-10-06）也印证过：它把 systemd 的 9598 掐掉、换成了自己的子进程，
此后 `systemctl --user is-active sentrix-api` **一直是 inactive**——运维看到的「服务在跑」
其实是个不受 systemd 管的裸进程。

**现在设上了**（`deploy/systemd/sentrix-photobench.service`）：

```ini
Environment=PHOTOBENCH_SENTRIX_SERVICE_UNIT=sentrix-api.service
```

走 `SystemdSentrixProcess` 后：`running_endpoint()` 读 `systemctl show` 的有效环境（权威记录），
**端点没变就不重启**，也就不去碰那个进程。

> 排查口诀：**「2.0 到底在跑哪个模型」看 drop-in；「9598 归谁管」看 `systemctl --user is-active`。**
> 两者不一致（单元 inactive 但端口有人听）就是踩了这条。

## 6. 迁移（从 1.0 换到 2.0）

**现在是并存期**：1.0 的 8091 / 4174 / 8771 **保持运行**，M3 之前是权威；2.0 并行起在
9598 / 9597。【转录】（S11 计划书 §2、设计文档）

### 6.1 数据目录必须独立（**qdrant 尤其**）

**【转录】**（`sentrix/config.py` `qdrant_dir`、`infrastructure/vector/qdrant_index.py` 模块头）：

- 2.0 用**独立的数据目录**：`data/`（默认 = 仓库根下 `data/`，由 `SENTRIX_DATA_DIR` 配）。
  里面是 `sentrix.db`、`media/`、`previews/`、`geo/`、`qdrant/`。
- **qdrant 必须独立**：1.0 用嵌入式 `QdrantClient(path=...)`，8091 进程**独占目录锁**。

**【实测】** 第二个进程打开同一目录会抛：

```
RuntimeError: Storage folder <dir> is already accessed by another instance of Qdrant client.
If you require concurrent access, use Qdrant server instead.
```

2.0 把这个异常翻成 `VectorIndexUnavailable`——**降级可以，静默不行**
（与 1.0「打印一行日志、接口照常返回空结果」的静默降级不同）。

> **实测更正（重要）**：任务书/计划口述「共享 qdrant 会让 2.0 **启动即失败**」——
> **实测不是**。2.0 的 qdrant 客户端是**惰性**的（`QdrantVectorIndex._get_client` 首次用时才连），
> 我把一个持锁进程占住 2.0 的 qdrant 目录后再 `create_app()`，**启动成功**（`mounted=True`，returncode 0）。
> 共享的真实后果是：**向量索引不可用 → 检索降级回 SQLite 精确扫描**（`retrieve_visual` 里
> `VectorIndexUnavailable` 被吞掉、回退 `sqlite_exact`），而 `backfill_visual_vectors.py`
> 会因为写不进镜像而失败。**结论不变：2.0 的 qdrant 必须独立**，但症状不是启动崩溃。

### 6.2 迁移步骤〔未实测〕

迁移**运行数据**（1.0 的 `sentrix.db`、媒体、评测历史）按**用户 2026-10-06 裁决：不迁**——
2.0 从空库起。**唯一搬过来的是评测标注**（问题+正确答案），因为那是人工标注、不可再生；
搬迁清单与理由见 `docs/refactor/2026-10-06-eval-data-migration.md`。

> 若将来要把 1.0 数据整体切到 2.0：**先停 1.0 的 8091**（否则它的 qdrant 锁会被带走/冲突），
> 再规划数据目录。**不要**让两个进程共享任何 `data/qdrant`。〔未实测〕

### 6.3 PhotoBench 的 `results/` 不再指向 1.0（2026-10-06 起）

**曾经**：单元里有一条 `Environment=PHOTOBENCH_RESULTS_ROOT=.../Sentrix-Home-Web/services/photobench/results`，
让 9597 列出 1.0 那 281 个 run（20 GB）。

**现在**：那条**整行删掉**了。不写死另一条路径是因为没必要——`photobench/config.py:86`
的缺省值 `APP_ROOT / "results"` 正是 2.0 自己的 `apps/photobench/results`。
少一行配置就少一处会漂的地方。

**【实测】**（改完 `make install-services` + `restart` 后）：

| 探活 | 结果 |
|---|---|
| `systemctl --user show sentrix-photobench -p Environment` | 空 |
| `GET /api/v1/runs` | `total: 0`（2.0 自己的空 results） |
| `GET /api/v1/manifests` | **仍列出 5 个 dataset**（album3 53 张照片、5 个 qa set） |

**最后一行是关键**：`results_root` 与 `data_root` 是**两个独立配置项**，
清掉前者不会伤到评测数据集——这正是这次改动的安全边界。

**空目录不会让 9597 崩**：`FileRunStore.iter_entries` 头一句是
`if not self._root.exists(): return`（`infrastructure/results/store.py`）。

> 代价（**有意的**）：PhotoBench 界面现在列出 **0 个 run**。那 281 个 run 是 1.0 的评测历史，
> 按裁决属「旧数据」，留在原处不动。要回头对照就把这一行加回去。

## 7. 重建索引

**【转录】**（两个脚本的 docstring，`scripts/backfill_text_vectors.py` /
`scripts/backfill_visual_vectors.py`）：

```bash
cd ~/Github/sentrix-home-web2.0

# 文本向量（T115d）
.venv/bin/python scripts/backfill_text_vectors.py [scope]     # scope 缺省 album1

# 视觉向量（W1）
.venv/bin/python scripts/backfill_visual_vectors.py [scope]   # scope 缺省 album1
```

**注意事项（逐条来自脚本 docstring / 依赖代码）**：

1. **幂等，可反复跑**：`IndexObservationText.index` / `IndexAssetVisual.index` 都是
   先查 `has_vector` 再嵌。**所以「本次写了 0 行」不是失败**——第二次跑本来就是 0。
2. **判据看「覆盖率」，不看本次写了几行**。脚本最后打印
   `文本向量覆盖率：covered/expected` / `视觉向量覆盖率：covered/N`。覆盖率是 0 且本该有数据时
   退出码 1——那是「嵌入侧压根没连上」，别当成「已经跑过了」。
3. **视觉回填必须在 API 停止时跑**（脚本 docstring 点名）：
   派生索引（Qdrant）是嵌入式本地实例，**同一份存储目录同时只能一个进程打开**。API 在跑时回填，
   权威存储照写，但每张图的镜像会以 `Storage folder ... already accessed by another instance`
   失败，**且重跑补不回来**（权威存储已有行 → 早返回 `already_indexed`，根本不会再走镜像）。
   ```bash
   systemctl --user stop sentrix-api.service
   .venv/bin/python scripts/backfill_visual_vectors.py [scope]
   systemctl --user start sentrix-api.service
   ```
4. **文本回填不受 qdrant 锁影响**（它走 `vector_repository` 的 SQLite 权威存储；qdrant 是派生镜像）——
   但**两者都要嵌入侧车在跑**：容器里 `text_embedder` 与 `visual_embedder` **是同一个 WeMM 实例**
   （`wemm_url = http://127.0.0.1:8102`）。
5. **视觉回填只补「当前 scheme 缺的那一行」，不是删旧索引**：换方案后旧 `model_name` 的向量原样留着，
   同一条资产可以并有多套模型的向量（唯一键含 `model_name`）。**人脸向量（buffalo_l 512 维）不在范围内**。
6. 脚本要从**仓库根**跑（它自己插 `apps/api/src` 到 `sys.path`，但 `load_settings()` 的 `data_dir`
   默认是相对 CWD 的 `data/`）。

**【未实测】** 这两个脚本本次**没有实际执行**；上文全部来自脚本 docstring、`container.py` 与
`qdrant_index.py` 的代码路径，非运行结果。

## 8. 故障处理

### 8.1 端口被占

【实测】用的诊断命令：

```bash
ss -ltnp | grep -E ':(9598|9597)\b'          # 谁在听
lsof -iTCP:9598 -sTCP:LISTEN                  # 按端口反查监听进程
systemctl --user status sentrix-api.service --no-pager
```

- 若 9598 被一个**不是 systemd 管的**进程占着（例如旧的 `make dev` 前台进程还活着），
  `systemctl --user start sentrix-api` 会起不来、日志里是 `address already in use`：
  ```bash
  journalctl --user -u sentrix-api -n 50 --no-pager
  ```
  **先清掉那个裸进程**（`kill <pid>`），再 `systemctl --user start`。
  **注意**：`systemd --user` 的单元 `Restart=on-failure`，崩溃会自动重拉；但 `stop` 发的 SIGTERM
  属正常退出，**不会**触发重启。
- ⚠️ 反查端口时**必须带 `-sTCP:LISTEN`**（脚本 `sentrix_process.py` 的注释点名的坑）：
  不加会把**连着这个端口的客户端**（keep-alive 连接池里的 httpx 客户端等）也列出来、被一起误杀。

### 8.2 `systemctl --user` 显示 `active` 但探活失败

**先确认「探活失败」是不是探错了路径**——两个服务的健康面不一样：

```bash
# 2.0 主 API：有 /api/v1/health
curl -s http://127.0.0.1:9598/api/v1/health
# {"status":"ok","version":"0.1.0","database":"ok"}     ← 【实测】

# 2.0 PhotoBench：**没有 health 路由**，探 /api/v1/health 会 404（正常）
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9597/api/v1/runs   # 200  ← 【实测】
```

`status` 的 `degraded` 只表示**库**有问题，进程是活的（1.0/2.0 同口径）。

再看进程与日志：

```bash
systemctl --user show sentrix-api --property=ActiveState --property=SubState --property=MainPID
ps -o pid,etime,cmd -p <MainPID>
journalctl --user -u sentrix-api -n 80 --no-pager
```

- **`active (exited)` 的假活**：1.0 的 `sentrix-vllm.service` 是 `Type=oneshot` +
  `RemainAfterExit=yes`（【转录】1.0 runbook）——显示 `active (exited)` 但**什么都没在跑**。
  2.0 的两个单元都是 `Type=simple`，**不会有这个假象**；但排查别台机器时要记得这条。
- 若 `MainPID=0` 且反复重启：看 `journalctl`，多半是启动期异常（见 8.3）。
- **`Linger` 没开**也会造成「昨天还好、今天没了」：见 §3.1。

### 8.3 2.0 报 qdrant 锁 / 向量检索降级

**症状**：检索结果变少 / 回退 SQLite；日志里出现
`Storage folder ... already accessed by another instance` 或
`派生索引在检索中途不可用，回退权威存储: ...`（`retrieve_visual.py`）。

**注意**：【实测】**不会**在启动时报错崩掉（qdrant 客户端是惰性的，见 §6.1）。

诊断：

```bash
# 1) 谁占着 2.0 的 qdrant 目录锁
ss -ltnp | grep -E ':(9598|8091)\b'          # 两个 API 都在跑？它们的数据目录是同一个吗
ls -la data/qdrant/.lock                      # 2.0 的锁文件
# 2) 确认 2.0 的 data_dir（默认是相对 CWD 的 data/）
systemctl --user show sentrix-api --property=WorkingDirectory
# 3) 确认没人和 1.0 共用目录：2.0 的 qdrant 派生自 SENTRIX_DATA_DIR，默认 repo/data
```

**修法**：2.0 与 1.0 **必须各用独立的数据目录**（本机已经独立：2.0 = `sentrix-home-web2.0/data`，
1.0 = `Sentrix-Home-Web/data`）。若发现共用，改 `SENTRIX_DATA_DIR` 指到 2.0 自己的目录再重启。

> 视觉回填在 API 跑着时也会打这条锁日志——那是 §7 的注意事项 3，停 API 再跑。

### 8.4 前端 404（dist 没构建）

**症状**：9598 或 9597 的 `/` 不是页面；日志里是 §5 那两条 warning。

```bash
ls apps/web/dist/index.html                  # 不存在 → 没构建
ls apps/photobench/web/dist/index.html
journalctl --user -u sentrix-api -n 50 --no-pager | grep '产物目录不存在'
cd apps/web && npx vite build
cd apps/photobench/web && npx vite build
systemctl --user restart sentrix-api.service sentrix-photobench.service
```

- **404 也可能是「路径该 404」**：`/api/v1/nope` 必须 JSON 404、`assets/missing.js` 必须 404
  （`main.py` 的 `SpaStaticFiles._is_client_route` 有意为之）。别把这些当成挂载坏了。
- PhotoBench 前端**没有 SPA 回落**（不引 react-router，UI 状态不进 URL），未知路径本就该 404。

## 9. 附：单元文件要点（排查时对照）

**【转录】**（`deploy/systemd/`）：

| 单元 | 关键行 |
|---|---|
| `sentrix-api.service` | `Type=simple`；`WorkingDirectory=%h/Github/sentrix-home-web2.0`；`ExecStart=...uvicorn --factory sentrix.main:create_app --host 0.0.0.0 --port 9598 --app-dir apps/api/src`；`Restart=on-failure` `RestartSec=5`；`WantedBy=default.target` |
| `sentrix-photobench.service` | 同上，但 `--port 9597 --app-dir apps/photobench/src`；**无 `Environment=`**（2026-10-06 起不再指向 1.0 的 results，见 §6.3） |

- `%h` = 当前用户 home。**换检出位置只需改单元里的路径两行**。
- 单元**刻意不用仓库外的 `EnvironmentFile`**：单元在仓库里、drop-in 是运行时状态，两者互不覆盖。
- `Restart=on-failure` + `WantedBy=default.target`：**崩溃自动重拉**、**开机自启**
  （前提：`systemctl --user enable` 过 + `Linger=yes`）。〔开机自启未实机重启验证〕
