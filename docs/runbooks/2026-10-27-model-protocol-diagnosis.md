# 2026-10-27 模型协议诊断与候选边界

截至本记录，六批共享建库均隔离，没有已验收共享基线、真实 QA 并发推荐值或 1167 题全集成绩。153 主服务未修改；100 只使用物理 GPU1，GPU0 原任务保持运行。新候选不能继承历史启动配置的容量成绩。

## 已证实的提前结束原因

100 的 tokenizer 和 xgrammar 使用 `<|im_end|>`（248046）作为结束符，原 generation_config 则使用 `<|endoftext|>`（248044）。实装 vLLM 0.26 的采样器把后者作为额外停止 token，而对应语法未把它视为结束符。在一条仍未闭合的 JSON 前缀上，离线语法接受 248044、拒绝 248046，导致模型可在语法未结束时提前 stop。

新实验仅在独立 generation_config 副本中把 EOS 改为 248046，未修改原权重或 tokenizer，也未添加输出上限。相同 B 采样的新请求完整复现旧请求的 10853 字符前缀，在原末尾的第 4315 个输出 token 生成 248044 后继续，再生成 1222 token，最终以 248046、stop、DONE 和完整 usage 结束。新输出为 5537 token、严格 JSON/schema 均通过。这是提前结束路径的直接对照证据。原始 token 离线重放全部通过同一语法；SSE 与整段 decode 的少量字符差异另行保留，不能泛称两条解码路径逐字符一致。

`--override-generation-config` 在实装 0.26 的相关 EOS 读取路径不生效，因此实验使用独立配置目录，并保存完整配置与启动哈希。原配置保持可恢复。

证据：内网 `runtime/ocr-eos-only-e1950d9d13d143ab918c289e4d636393/eos-only-derived-report.json`，包括唯一请求 ID、实际 token 位置、终态、使用量与服务归零记录。私有图片、OCR 内容和生成正文不进入 Git。

## 尚未解决的 OCR 循环

EOS 对齐只修正已复现的提前 stop 路径。原采样仍在 `ocr_text` 中出现同一六字符周期，未闭合字符串持续增长。单独增加 frequency_penalty=0.2 的 B 请求虽然完整结束，但 OCR 保真不合格，因此未采用。随后仅关闭异步调度，原采样仍出现相同循环；约 155 秒人工诊断取消并保留结果未知。未扩大到 C4 或固定 16 图。

无异步组峰值 running1、waiting0、KV 约 2.35%，守卫无资源故障，结束后队列归零；没有证据把该循环归因于资源容量或上下文不足。人工取消不是正常完成、输出长度故障或 Agent 回答质量 0 分。固定周期判据仅用于提出人工诊断取消，不作为产品自动截断机制。

证据：内网 `runtime/ocr-noasync-only-20039cd3ec7c4a44845e169b678cff81/noasync-derived-report.json`。真实 Agent/VLM 仍不设置输出 token 或字符串长度上限。

## 独立引擎候选

100 已有 vLLM 0.22 环境的 CPU 预检通过：vLLM 内置 Qwen3.5 配置、tokenizer、processor、模型 registry 以及现有启动参数均可解析。普通 Transformers AutoConfig 不认识该架构，不能与 vLLM 的内置路径混称。该环境默认 Omni 插件存在 Python 版本不兼容；候选仅在独立进程设置 `VLLM_PLUGINS=`，没有修改共享环境或安装包。

首个 GPU 启动在加载权重和派发请求前失败：该版本把 CUDA_VISIBLE_DEVICES 的 UUID 当整数解析。后续独立尝试须通过 PCI bus 排序及 CUDA 设备身份核对，绑定原 GPU1，再进入 GPU 内核、协议及原生窗口验收。CPU 预检或启动修正均不代表实际推理通过。

## 123 的准入修正与原生窗口

123 地址为 192.168.1.123，使用项目私有 Docker socket。原 Sentrix 9598、PhotoBench 9596 和 BGE 8101 保持原进程身份。seq4 的首次启动在加载权重前被显存准入检查拒绝：约 29.63 GiB 可用，低于 0.50×61.37 GiB 的门槛。原 seq1 恢复亦遇同一门槛，所以不能据此宣称 seq4 的推理容量失败。

实装 0.19 即使显式指定 KV 字节数，仍先执行此准入检查。新独立配置把 gpu_memory_utilization 改为 0.45，保留 10 GiB KV 和 262144 总窗口。先恢复 seq1 基础协议，再仅把 seq1 改为 seq4。新 seq4 配置通过五项基础协议及一次实际满窗请求：261632 输入加 512 输出，379.333 秒，首响应 340.475 秒，结束 DONE/length；随后 running、waiting 和 KV 归零，启动身份不变。这里的 512 仅是合成容量探针预留，不用于真实 QA 或观察。

启动、协议及满窗各自有守卫的区间均没有新增换出；启动结束到协议开始约 99 秒的离线计量间隙，累计换出增加 516 页，约 2.02 MiB。间隙缺少连续采样，不能称孤立换出，也不能归因于离线 renderer。原生输入使用同实装 vLLM HfRenderer 的隔离离线路径计量，未调用在线 /tokenize；该进程确实初始化了 CUDA 上下文，不能称完全无 CUDA。

这只证明新 seq4 配置下单个满窗请求通过；不代表四个满窗并发、30 分钟资格或真实 QA 推荐并发。新旧配置身份、各自原始指标和回滚记录分别保留。下一步独立验证历史问题图与固定图片集，再决定是否作为统一记忆生产者。
